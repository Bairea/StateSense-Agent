## 3. 回放器：把「需要等」变成「不需要等」

```
$ uv run python -m statesense --replay all
PASS  ladder
PASS  outcome
PASS  gates
PASS  degraded
PASS  sleep_gap
WARN  high_risk_minutes=65 高于 window_minutes=60：ent 是窗口内条目分钟数之和，
      不可能超过窗口长度，因此 HIGH_RISK_PASSIVE_CONSUMPTION 不可达，
      其专属动作永远不会被选中。修正方向：把 high_risk_minutes 降到窗口以内，
      或加长 window_minutes
```

**这条输出把 V0 验证日志 §7 的前两条从「未验证」变成「已验证（机制层面）」：**

| V0 §7 原条目 | 现在的状态 |
|---|---|
| 真实长时段被动消费触发干预 | **机制已验证**：`ladder` 跑完 90 分钟虚拟时间，证明 20/40/65 阶梯真的产生状态迁移、且在 `PASSIVE_CONSUMPTION` 真的触发干预 |
| T+10min 行为回执实际落行 | **机制已验证**：`outcome` 用两个对照剧本证明 `outcomes` 表真的落行，且 `disengaged` / `continued` 两个标签都正确 |

`outcome` 剧本的两个对照：

- 娱乐在触发点**停止** → `before = 10` 分钟、`after = 0` 分钟 → `disengaged`
- 娱乐**继续** → `before = after = 10` 分钟 → `continued`

`gates` 剧本覆盖了 8 次 `daily_cap` 触顶与 cooldown 边界（300 分钟虚拟时间、61 轮）：

- 触发次数恰好等于 `daily_cap = 8`，一次不多
- 存在被 `cooldown` 以「不足阈值」挡下的轮次（`value < 30`）
- 任意两次干预间隔都 ≥ 30 分钟
- 存在以 `daily_cap` 为首个失败闸门的轮次

`degraded` 剧本守住核心安全属性：`data_status = unreachable` 时逐轮落行、`skipped = 1`、
**没有任何干预发生**。这正是 V0 审查发现的最严重问题之一（非 ok 数据下仍写 `state=NORMAL`
且无法分辨）的回归锁。

`sleep_gap` 剧本证明健康信号成立：200 分钟空档不落 `evaluations` 行，但落一条
`run_events(kind='sleep_gap', detail='200.0')`。

## 5. 实施中发现并修正的缺陷

| # | 缺陷 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | `ScriptedReader` 用 `captured_at` 当窗口末端，而真实 `ActivityReader.read(start, end, ...)` 用 `start`/`end` | `outcome` 剧本的 `stopped` 分支算出 `ent_before=0.0`（应为 10.0）→ 回执永远是 `no_data` | `snapshot_at` 改为按 `start`/`end` 裁剪，并补一条专门的测试 |
| 2 | `--replay` **不可重复**：上一轮的库文件还在，行数累加 | 端到端跑**第二遍**时 `degraded` 从 6 行变 12 行、`sleep_gap` 从 1 行变 2 行。pytest 里没暴露，因为 `tmp_path` 每次是新的 | `check_scenario` 每次重建工作目录，并补两条重复性测试 |
| 3 | 计划里的 `run_events` 测试用同一时刻插两条 | 写测试时发现 `at` 是主键且用 `INSERT OR REPLACE`，第二条会覆盖第一条 | 测试改用不同时间戳，另加一条「同刻幂等」测试 |
| 4 | `test_report_config` 的 helper 向已含 `[report]` 的示例追加同名表 | TOML 报重复表，9 个测试全红 | helper 先摘掉示例里的 `[report]` 节；另加「示例值必须等于代码默认值」的漂移测试 |
| 5 | `test_gate_breakdown_survives_corrupt_trace` 断言「坏数据仍计数」 | 语义写反了 —— 坏行应当跳过、其余照常 | 改成两行数据、坏一行、断言好行仍被统计 |
| 6 | 配置带 UTF-8 BOM 时 `tomllib` 报 `Invalid statement (at line 1, column 1)` | **真实联调**：用 PowerShell 生成临时配置时带上 BOM，位置指向文件开头，用户完全看不出原因。Windows 记事本默认就写 BOM | `load_config` 显式剥掉 BOM，并补两条测试 |
| 7 | TOML 语法错误**没有被包成 `ConfigError`**，`main` 接不住 | **真实联调**：用户看到的是 Python traceback 加退出码 1，而不是「配置错误：…」加退出码 2 | 解析失败包成 `ConfigError`；补一条断言「无 Traceback」的 CLI 测试 |
| 8 | `--format json` 会输出裸 `Infinity`，不是合法 JSON | **真实联调**：V0 时期写的旧行 `gate_trace` 里存着 `Infinity`（表示「从未干预过」），`report` 如实读出并原样序列化。规格 §5.4 明说 JSON 是给 `jq` 用的，而 `jq` 会直接拒绝 | `render_json` 把非有限浮点转 `null`（正好对应 `value=None` 的既有语义），并用 `allow_nan=False` 兜底；补两条严格解析测试 |

**缺陷 1 与 2 都是"回放器验证回放器"发现的。** 缺陷 2 尤其说明问题：一个不可重复的
验证工具比没有验证工具更糟 —— 它会在第二次运行时给出假结果。这条只会在真实重复执行时暴露，
纯单元测试永远抓不到。

**缺陷 6、7、8 只有真实跑起来才会暴露。** 前六个都在 `pytest` 全绿的情况下存在 ——
它们全部落在"测试覆盖不到的接缝"上：真实编码环境、真实错误路径、旧版本遗留的数据。

缺陷 8 尤其值得记一笔：它**不是本次引入的**，是 V0 时期写进库的旧数据暴露了 report 的
一个健壮性缺口。`report` 读的是历史行，包括旧版本写的行 —— 这一条以后还会再遇到。

## 6. 结构性发现（未修，交 owner 决定）

> **两项都已有结论（2026-09-18），见 §11。** 6.1 已按「降到窗口以内」解决
> （`high_risk_minutes = 55`），并且真实数据已确认该状态可达；6.2 的 0.7 阈值
> 保留为起点，等跨天分布再调 —— 它是判据 4 的一部分，不该现在拍板。
> 下面两节保留当时的推理过程，不改写。

### 6.1 `HIGH_RISK_PASSIVE_CONSUMPTION` 在默认配置下不可达

`ent_minutes` 是窗口内条目分钟数之和，**不可能超过窗口长度**。而默认配置：

```
window_minutes     = 60
high_risk_minutes  = 65
```

于是 `ent >= 65` 永远不成立。后果：

- `HIGH_RISK_PASSIVE_CONSUMPTION` 是**死状态**
- 动作池里 `applies_to = ["HIGH_RISK_PASSIVE_CONSUMPTION"]` 的 `reading`（读一段《道德经》）**永远不会被选中**

`ladder` 剧本的 90 分钟连续娱乐实测 `ent` 上限为 60，从未触到 65。

**真实数据把这个前提测了一半。** §4.4 第 ⑤ 项的探测显示：单个 60 分钟窗口内
`sum(entries)` 最大达到 **60.10** —— 确实能超过窗口长度，但只超 0.17%。
要到 65 需要 108% 的重复计数。所以结论不变，只是理由要改写：

> 不是"数学上不可能"，而是"需要 8% 的重复计数，实测只有 0.17%"。

同时该探测也**没有发现多显示器造成的成倍重复**（§4.4 第 ⑥ 项：`entries_minutes`
精确等于 `total_active_minutes`）。

这不是实现缺陷，是 V0 继承自 `ref1.md` 的 20/40/65 刻度与 60 分钟窗口不一致。
两个修法各有代价：

| 修法 | 代价 |
|---|---|
| `high_risk_minutes` 降到窗口以内（如 55） | 偏离 `ref1.md` 的 65 刻度 |
| `window_minutes` 加长到 70+ | 改变分析窗口；V0 规格里「60 分钟窗口内 `ent>=40` 隐含 `ratio>=0.667`」的推导需重算 |

**本次不改，只让它在每次 `--replay` 时以 WARN 现形。** `structural_findings()` 会持续提示，
直到配置改对为止 —— 有测试锁住这个行为。

### 6.2 漏判锚点的 0.7 阈值在清单薄弱时会偏噪

种入数据时，9 轮里 6 轮触发了漏判锚点 —— 因为那些轮次只有 5 分钟娱乐、其余 55 分钟
是"未命中任何规则"的活动。这在语义上**是对的**（60 分钟没被任何规则解释确实值得看），
但它说明锚点的信噪比直接取决于分类清单配得有多全。

这与 §8 的分类清单个性化是同一件事的两面：清单越全，锚点越准。
规格已写明 `0.7 是起点，用真实分布再调`。

## 10. 傍晚的链路修复（2026-09-17 19:00–20:30）

下午的监控数据是**废的**：`ok=17 / unreachable=63`，`ok` 止于 13:57。daemon 本身没错 ——
它如实记下了 63 轮 `skipped=1`，正是「真的正常」与「没采到数据」可区分的设计在起作用。
但采不到数据，监控就是空的。

排查下去发现是**四个互相掩盖的基础设施缺陷**，一个套一个。它们没有一个能靠单元测试
发现，而且每一个都伪装成「一切正常」：

| # | 缺陷 | 现象 | 修法 |
|---|---|---|---|
| 1 | recorder 挂在**会话后台任务**上 | 与第一次 daemon 同样的静默回收，13:58 消失 | 移入任务计划程序 |
| 2 | **端口 3030 被 Docker 占着**（`com.docker.backend`） | Screenpipe 绑不上却仍有进程。「端口在监听」一直是 Docker 在答，`/activity-summary` 返回 404 | recorder 改用 `--port 3131`；`config.toml` 与启动器同步 |
| 3 | 任务里**直接跑 exe**（无控制台、无重定向） | 进程在、日志一行不写、端口没人听。改用 PowerShell 管道重定向也不行（退出码 1，日志停在「设置进程优先级」） | 用 `Start-Process -RedirectStandardOutput`（文件句柄直接交给子进程，不经过 PowerShell 管道） |
| 4 | **任务计划服务的环境块是旧的** | 用户级环境变量在注册表里、却不在新进程环境块里。daemon 读不到 `SCREENPIPE_LOCAL_API_KEY`，每轮鉴权失败 → 全 `unreachable` | 启动器从注册表读回该变量再启动 |

**缺陷 2 最阴险**：`Test-NetConnection 3030` 返回 True，进程列表里 screenpipe 也在，
一切看起来正常。真正的判据是**看谁在监听**：

```powershell
Get-NetTCPConnection -LocalPort 3030 -State Listen | Select-Object OwningProcess
```

**缺陷 4 的教训**：`[Environment]::SetEnvironmentVariable(..., 'User')` 只写注册表，
不会广播 `WM_SETTINGCHANGE`，已在运行的进程（含任务计划服务）环境块不会更新。
任何靠它取密钥的常驻任务都必须自己从注册表读一遍。

起因是「把当前已有的 screenpipe 日志与监测日志拿出来看看」。看的结果是：
**Screenpipe 的日志很健康，监测进程的日志是空的** —— 而这不是故障，是设计后果，
但它正好掩盖了一次真实的重启。

### 12.1 当时的状况

| 日志 | 状态 |
|---|---|
| `D:\Screenpipe\screenpipe.2026-09-18.0.log` | 133 行，`api_usage_5min: 1~4 requests` 每 5 分钟一条 —— **这是「daemon 确实在和 Screenpipe 说话」的交叉证据** |
| `D:\tmp\recorder.out.log` | 14.9 KB，与上面同源 |
| `D:\tmp\recorder.err.log` | 权限自检 + 推广提示，无错误 |
| `D:\tmp\daemon.out.log` | **0 字节** |
| `D:\tmp\daemon.err.log` | **0 字节** |

`daemon.*.log` 是空的，两个原因叠加：

1. **健康的一轮什么都不打印。** daemon 只在异常时 `log.warning`（休眠空档、本轮异常），
   成功路径一行不写 —— 它的记录是**库**，不是日志。所以 0 字节本身符合设计。
2. **每次重启都把上一份截断成 0。** `Start-Process -RedirectStandardOutput` 是覆盖写。

### 12.2 因此暴露的问题

对照 tick 间隔，2026-09-18 12:36:48 那一轮比正常的 5.0 分钟短了 2.2 分钟 ——
说明 **12:36:47 又发生了一次我没做的重启**（上一次同类现象记在 §10，当时结论是
「未 root-cause」）。而它在系统里没留下任何证据：

| 本该留下痕迹的地方 | 实际情况 |
|---|---|
| `daemon.out.log` / `daemon.err.log` | 被覆盖成 0 字节 |
| `run_events` | 空 —— 两处补丁只覆盖 `run_tick_guarded` 抓到的异常，**进程级退出不走那条路** |
| 任务计划程序 | `LastTaskResult=0`，也就是"正常结束" |
| 唯一线索 | 一次 2.8 分钟的 tick 间隔 |

**V0.5 的全部意义就是回答「V0 到底在不在跑」，而这次退出恰好落在它答不出来的那个洞里。**

顺带核对过进程树，确认没有重复实例（只有一个 daemon 链、一个 recorder 链）：

```
wscript → powershell → uv → python(.venv) → python(real)     ← daemon
wscript → powershell → screenpipe                            ← recorder
```

### 12.3 补了什么

| # | 修补 | 位置 |
|---|---|---|
| 1 | **常驻启动行**：pid / 分支 / schema / 库 / Screenpipe 地址 / 通道 / 节奏 | `__main__.py::log_startup` |
| 2 | **`run_forever` 结束时打一行**，异常路径另记一行原因 | `scheduler.py::run_forever` |
| 3 | **日志走 stdout、编码钉 UTF-8、不缓冲** | `__main__.py::main` + `run-daemon.ps1` |
| 4 | **旧日志改名留档**（保留最近 5 份） | `run-daemon.ps1` / `run-recorder.ps1` |

`log_startup` 里的**分支**是特意加的：§5 记录过「从错误的分支起过 daemon」那次事故
（它把库降级回 v3 并写了一堆 `entries_minutes=0` 的假行，当时靠事后对库才发现）。
启动行带分支名，这种事一眼可见。读法是不起子进程地直接解析 `.git/HEAD`，
并同时支持 worktree 的 `gitdir:` 形式与 detached HEAD。

### 12.4 修补过程中自己踩的两个坑

**坑一：`edit` 工具把 `.ps1` 的 UTF-8 BOM 抹掉了。** 而 PowerShell 5.1 读无 BOM 的
UTF-8 `.ps1` 会按 GBK 解码 —— 正是 §10 记录过的那个坑，脚本会直接语法错误。
发现方式是把 BOM 检查加进了流程，并补了一个 `fix-bom.py` 每次改完复核。
三个脚本现在都通过 AST 解析校验。

**坑二：第一版补丁把日志写成了 GBK。** Windows 上把 stdout 重定向到文件时，
Python 用的是当前 ANSI 代码页。实测：`daemon.out.log` 里那个 `0xb3` 解不出 UTF-8，
按 GBK 解则是「常驻启动 pid=… 分支=…」。补法是 `PYTHONIOENCODING=utf-8`。
**日志的第一条要求就是它自己得能被读出来** —— 一个编码不对的日志和不存在的日志
在排查时一样没用。

### 12.6 仍未解决的

按 §7.7 的三种结局，重跑一段时间后可以这样判：

- 有「常驻循环异常中止」→ 原因在同一行，直接修；
- 只有「常驻循环结束」→ 循环自己走完了，那是缺陷本身；
- 两句都没有而进程没了 → 外力所杀，该去查任务计划程序与系统事件日志。
