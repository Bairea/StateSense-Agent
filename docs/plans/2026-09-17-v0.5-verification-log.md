## 3. 回放器：把「需要等」变成「不需要等」

```
$ uv run python -m statesense --replay all
PASS  ladder
PASS  outcome
PASS  gates
PASS  degraded
PASS  sleep_gap
WARN  high_risk_minutes=65 高于 window_minutes=60：ent 是窗口内条目分钟数之和，
      不可能超过窗口长度，因此 HIGH_RISK_PASSIVE_CONSUMPTION 不可达，
      其专属动作永远不会被选中。修正方向：把 high_risk_minutes 降到窗口以内，
      或加长 window_minutes
```

**这条输出把 V0 验证日志 §7 的前两条从「未验证」变成「已验证（机制层面）」：**

| V0 §7 原条目 | 现在的状态 |
|---|---|
| 真实长时段被动消费触发干预 | **机制已验证**：`ladder` 跑完 90 分钟虚拟时间，证明 20/40/65 阶梯真的产生状态迁移、且在 `PASSIVE_CONSUMPTION` 真的触发干预 |
| T+10min 行为回执实际落行 | **机制已验证**：`outcome` 用两个对照剧本证明 `outcomes` 表真的落行，且 `disengaged` / `continued` 两个标签都正确 |

`outcome` 剧本的两个对照：

- 娱乐在触发点**停止** → `before = 10` 分钟、`after = 0` 分钟 → `disengaged`
- 娱乐**继续** → `before = after = 10` 分钟 → `continued`

`gates` 剧本覆盖了 8 次 `daily_cap` 触顶与 cooldown 边界（300 分钟虚拟时间、61 轮）：

- 触发次数恰好等于 `daily_cap = 8`，一次不多
- 存在被 `cooldown` 以「不足阈值」挡下的轮次（`value < 30`）
- 任意两次干预间隔都 ≥ 30 分钟
- 存在以 `daily_cap` 为首个失败闸门的轮次

`degraded` 剧本守住核心安全属性：`data_status = unreachable` 时逐轮落行、`skipped = 1`、
**没有任何干预发生**。这正是 V0 审查发现的最严重问题之一（非 ok 数据下仍写 `state=NORMAL`
且无法分辨）的回归锁。

`sleep_gap` 剧本证明健康信号成立：200 分钟空档不落 `evaluations` 行，但落一条
`run_events(kind='sleep_gap', detail='200.0')`。

## 4. 观测层

### 4.1 空库

```
$ uv run python -m statesense --report --config config/config.toml --db <空库>
概览
  区间内无任何评估记录。

结论：进程从未跑起来，或库路径不对。
exit=0
```

空库不是错误 —— 「进程从未跑起来」本身就是观测结论。

### 4.2 种入数据的完整视图

用手工种入的 9 轮评估（含一次被 `ratio_min` 挡下、一次真触发、一轮取不到数据、
一个 Brotato 式漏判锚点、一处 200 分钟缺口）跑 `--views all`，六个视图全部有输出：

```
判定面
  评估轮数    9
  状态分布    NORMAL=7  PASSIVE_CONSUMPTION=2
  data_status ok=8  unreachable=1
  skipped     1（这些轮的 state 不代表「真的正常」）

闸门面
  各闸门阻挡  state_min=6  ratio_min=1
  占比分布    0.0-0.1=5  0.1-0.2=1  0.7-0.8=1  0.8-0.9=1
  该提醒未提醒 1 轮（state_min 通过却被后续闸门挡下）
    2026-09-16 20:20:00+08:00  ratio_min  value=0.7 阈值=0.75

干预面
  触发次数    1
  用户回执    accepted=1
  被 cooldown 挡 0 轮   被 daily_cap 挡 0 轮

效果面
  回执分布    disengaged=1
  干预前娱乐  48.0
  干预后娱乐  4.0
  按用户回执分层（V0 规格 §16 风险 6 要求的缓解措施）：
    accepted   disengaged=1

疑似漏判（这一轮有活动，但规则一条都没命中）
  2026-09-16 20:35:00+08:00  活跃=59.9  未归类=59.9（100.0%）  明细缺失=0.0
```

**效果面的分层是 V0 规格 §16 风险 6 写明要做、而 V0 里没有任何地方能执行的那件事。** 现在它落地了。

概览视图同时给出了缺口及其成因：

```
  缺口        1 处
    2026-09-16 20:35:00+08:00 → 2026-09-16 23:55:00+08:00   200.0 分钟
      有运行事件记录：sleep_gap(200.0)
```

同一处缺口若**没有**运行事件记录，输出会写成「无运行事件记录 → 进程当时不在运行」——
这正是本版本要消灭的那个二义性的正面表述。

### 4.3 schema 守卫在真实旧库上生效

本机 `config/statesense.db` 是 V0 测试遗留的 **v3 旧库**：


`--report` 拒绝读取并拒绝迁移 —— 它承诺只读，就不该顺手改库。

## 5. 实施中发现并修正的缺陷

| # | 缺陷 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | `ScriptedReader` 用 `captured_at` 当窗口末端，而真实 `ActivityReader.read(start, end, ...)` 用 `start`/`end` | `outcome` 剧本的 `stopped` 分支算出 `ent_before=0.0`（应为 10.0）→ 回执永远是 `no_data` | `snapshot_at` 改为按 `start`/`end` 裁剪，并补一条专门的测试 |
| 2 | `--replay` **不可重复**：上一轮的库文件还在，行数累加 | 端到端跑**第二遍**时 `degraded` 从 6 行变 12 行、`sleep_gap` 从 1 行变 2 行。pytest 里没暴露，因为 `tmp_path` 每次是新的 | `check_scenario` 每次重建工作目录，并补两条重复性测试 |
| 3 | 计划里的 `run_events` 测试用同一时刻插两条 | 写测试时发现 `at` 是主键且用 `INSERT OR REPLACE`，第二条会覆盖第一条 | 测试改用不同时间戳，另加一条「同刻幂等」测试 |
| 4 | `test_report_config` 的 helper 向已含 `[report]` 的示例追加同名表 | TOML 报重复表，9 个测试全红 | helper 先摘掉示例里的 `[report]` 节；另加「示例值必须等于代码默认值」的漂移测试 |
| 5 | `test_gate_breakdown_survives_corrupt_trace` 断言「坏数据仍计数」 | 语义写反了 —— 坏行应当跳过、其余照常 | 改成两行数据、坏一行、断言好行仍被统计 |

**缺陷 1 与 2 都是"回放器验证回放器"发现的。** 缺陷 2 尤其说明问题：一个不可重复的
验证工具比没有验证工具更糟 —— 它会在第二次运行时给出假结果。这条只会在真实重复执行时暴露，
纯单元测试永远抓不到。

## 6. 结构性发现（未修，交 owner 决定）

### 6.1 `HIGH_RISK_PASSIVE_CONSUMPTION` 在默认配置下不可达

`ent_minutes` 是窗口内条目分钟数之和，**不可能超过窗口长度**。而默认配置：

```
window_minutes     = 60
high_risk_minutes  = 65
```

于是 `ent >= 65` 永远不成立。后果：

- `HIGH_RISK_PASSIVE_CONSUMPTION` 是**死状态**
- 动作池里 `applies_to = ["HIGH_RISK_PASSIVE_CONSUMPTION"]` 的 `reading`（读一段《道德经》）**永远不会被选中**

`ladder` 剧本的 90 分钟连续娱乐实测 `ent` 上限为 60，从未触到 65。

这不是实现缺陷，是 V0 继承自 `ref1.md` 的 20/40/65 刻度与 60 分钟窗口不一致。
两个修法各有代价：

| 修法 | 代价 |
|---|---|
| `high_risk_minutes` 降到窗口以内（如 55） | 偏离 `ref1.md` 的 65 刻度 |
| `window_minutes` 加长到 70+ | 改变分析窗口；V0 规格里「60 分钟窗口内 `ent>=40` 隐含 `ratio>=0.667`」的推导需重算 |

**本次不改，只让它在每次 `--replay` 时以 WARN 现形。** `structural_findings()` 会持续提示，
直到配置改对为止 —— 有测试锁住这个行为。

### 6.2 漏判锚点的 0.7 阈值在清单薄弱时会偏噪

种入数据时，9 轮里 6 轮触发了漏判锚点 —— 因为那些轮次只有 5 分钟娱乐、其余 55 分钟
是"未命中任何规则"的活动。这在语义上**是对的**（60 分钟没被任何规则解释确实值得看），
但它说明锚点的信噪比直接取决于分类清单配得有多全。

这与 §8 的分类清单个性化是同一件事的两面：清单越全，锚点越准。
规格已写明 `0.7 是起点，用真实分布再调`。
