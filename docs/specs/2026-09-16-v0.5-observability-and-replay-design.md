# StateSense-Agent V0.5 技术规格：可验证与可观测

> 状态：**待评审**
> 前置：V0（`docs/specs/2026-09-16-v0-state-intervention-design.md`，已合并）
> 本规格不修改 V0 的判定逻辑、闸门语义与投递通道。

---

## 1. 背景与问题

V0 已交付：采集 → 判定 → 闸门 → 动作 → 投递 → 双轨回执 → 存储的完整链路，154 个测试全绿。

但 V0 留下一个不对称：

| | 定义 | V0 现状 |
|---|---|---|
| **测（test）** | 给定输入 → 期望输出，可重复、可断言 | 154 个，6.6 秒 |
| **观测（observe）** | 真实运行中发生了什么，不可重复，只能记录 + 回看 | **写入完整，读出为零** |

"读出为零"的具体含义：`Store` 的公开方法全是写入与运行时判定用的（`insert_*` / `fetch_*` / `due_interventions` / `last_intervention_at` / `intervention_count_since`），**没有一个是给人看的聚合查询**；CLI 只有 `--check`（当下快照）/ `--once`（一行）/ `--daemon`。**没有任何命令能回答"过去三天发生了什么"。**

### 1.1 三个未验证项

V0 验证日志 §7 的诚实清单：

| 项 | 状态 | 未验证的原因 |
|---|---|---|
| 真实长时段被动消费触发干预 | 未验证 | 需要真实刷 40+ 分钟 |
| T+10min 行为回执实际落行 | 未验证 | 同上 |
| `--daemon` 与任务计划程序注册 | 未验证 | 属部署动作 |

**关键判断：前两项之所以未验证，只是因为它们需要"等"，不是因为难测。** 它们的触发条件是时间的流逝，而不是输入的组合 —— 而这可以用注入时钟 + 注入数据源在秒级内复现。

### 1.2 一个数据可信度问题

`evaluations` 只存聚合分钟数（`ent` / `gray` / `work`），**不存窗口条目**。而分类清单 100% 由配置驱动，代码里没有内置默认（`config.py:180` 只校验 `entertainment` 非空）。

实测后果（验证日志 §10.1）：

```
取到 24 条窗口记录，总活跃 59.9 分钟
    46.9 分钟  Brotato          ← 游戏，被判成 NORMAL
state=NORMAL  intervened=False  note=ratio_min 未通过（0.04 vs 阈值 0.75）
```

刷了 47 分钟游戏，`ent = 0`，系统判定 `NORMAL`。

**并且实际的 `config/config.toml` 与 `config/config.example.toml` 逐字节相同** —— 分类清单从未按本人配置过。清单里放的是平台名（`steam`、`epic games`、`battle\.net`、`wegame`），而 Steam 启动的游戏，进程名与窗口标题都是游戏自身，不含平台关键词。

**这卡在 V0.5 的要害上**：`ratio = ent / total_active`。若真实数据里游戏占大头，用这份数据校准 `ratio_min` 就是在**用一份系统性漏掉最强娱乐信号的数据**做决定。

### 1.3 一个二义性

`ActivityReader.read()` **永不抛异常** —— 任何异常、非 200、JSON 坏掉、`data_status` 不认识，全部走 `_degraded()` 返回 `data_status='unreachable'` 的快照，而 `_evaluate_tick` 对每一轮都调 `insert_evaluation`。

**所以 `evaluations.data_status` 已经是一份逐 tick 的完整断连日志。健康信号不需要心跳表。**

但只有三种情况**不落行**，而它们在库里完全无法区分：

| # | 情况 | 代码位置 | 结果 |
|---|---|---|---|
| a | 休眠/唤醒空档 > 2×窗口 | `scheduler.py:111` 提前 return | 不落行（**有意跳过**） |
| b | 进程根本没在跑 / 死了 | —— | 不落行 |
| c | tick 内抛异常 | `run_forever` 的 `except Exception` | **只写日志，不落库** |

跑 5 天中间断了 6 小时，report 只能说"有 6 小时没记录"，无法回答是合盖睡了、进程崩了、还是崩在日志里了。

## 2. 成功判据

V0.5 只回答一个问题：

> **V0 到底在不在跑，跑出来的数据能不能用？**

具体判据，逐条可证伪：

| # | 判据 | 证伪方式 |
|---|---|---|
| 1 | 五个回放剧本全过，其中 `ladder` 与 `outcome` 把 §1.1 的前两条从未验证变为已验证 | 任一剧本失败 |
| 2 | `--report` 能回答四个问题：它在跑吗 / 为什么没提醒我 / 提醒了几次 / 有用吗 | 任一问题答不上 |
| 3 | 挂常驻跑满 5 天，report 的缺口视图与实际睡眠、重启记录对得上 | 缺口无解释或解释错误 |
| 4 | `ratio_min` 做出一个**有依据**的判断（调或不调均可，但必须有 `ent_ratio` 分布支撑） | 无数据支撑就下结论 |
| 5 | 现有 154 个测试不退化 | 任一失败 |

**第 4 条是刻意的：V0.5 不承诺"把 0.75 改成某个更好的数"。** 承诺改数值，等于把一个必须由数据回答的问题在规格里偷偷写死。

## 3. 非目标

- **不做自动分类推断。** 四个候选方向（人工补游戏名 / 外部进程映射表 / 全屏启发式 / 保持现状）没有一个是干净的：换游戏就失效、破坏 0 依赖、Screenpipe 的 `frames` 里没有全屏标志。V0.5 只让漏判**显形**，不替人猜修法。
- **不改判定逻辑、闸门语义、投递通道。** 这些属 V0 契约。§9 新增的 `entries_minutes` 是**派生字段**，只用于观测，**不参与 `classify` 与任何闸门判定** —— 状态结论与 V0 逐位一致。
- **不做实时告警通道。** 见 §7.5。
- **不引入 LLM**，`Wording` 接口保持原样。
- **不新增窗口内容的持久化。** 见 §5.3。
- **不做 V1 的"什么干预最有效"分析。** V0.5 只把所需数据变得可读。

## 4. 架构

### 4.1 分层

```
┌──────────────────────────────────────────────┐
│ __main__.py                                  │
│   --check / --once / --daemon    （V0）      │
│   --report / --replay            （V0.5 新增）│
└────────────┬─────────────────────────────────┘
             │
     ┌───────┴────────┬──────────────┐
     ▼                ▼              ▼
┌─────────┐   ┌─────────────┐  ┌──────────┐
│ report/ │   │  replay/    │  │scheduler │
│ 聚合+渲染│   │ 剧本+驱动    │  │  （V0）  │
│ （纯函数）│   │             │  │          │
└────┬────┘   └──────┬──────┘  └────┬─────┘
     │               │              │
     ▼               ▼              ▼
┌──────────────────────────────────────────────┐
│ store/   只读查询（V0.5 新增）+ 写入（V0）    │
└──────────────────────────────────────────────┘
```

`report/` 与 `replay/` **都只透过 `store/` 与既有接口访问数据**，不直接写 SQL、不绕过 `Store`。

### 4.2 组件职责边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| `store/db.py` | 拥有 SQL 与 schema 知识；提供**只读查询方法**返回原始行 | 聚合、渲染、判断 |
| `report/` | 聚合（纯函数）+ 渲染（纯函数） | SQL、网络、写库 |
| `replay/` | 剧本模型 + 合成快照 + 驱动 `Scheduler` | 重新实现判定逻辑 |
| `activity/base.py` | `ActivitySource` Protocol | 任何实现 |
| `scheduler.py` | tick 主循环（V0）；V0.5 只补 `run_events` 落行 | 观测 |

**分工原则：`Store` 交出"行"，`report/` 交出"意思"。** 聚合逻辑是纯函数，因此能被现有的测试体系覆盖，不需要数据库或网络。

### 4.3 一次 `--report` 的数据流

```
config.toml ──► Store（只读查询）──► rows ──► report 聚合（纯函数）
                                                  │
                            ┌─────────────────────┤
                            ▼                     ▼
                      text 渲染              json 渲染
                            │
                            └──► stdout（绝不写库）

可选：--from-screenpipe ──► ActivityReader ──► Screenpipe（只读回查）
```

### 4.4 四条边界原则

1. **report 只读。** 绝不写库 —— 避免"看数据把数据看了坏"。实现上由 `Store` 的只读方法与"report 不构造写入语句"共同保证。
2. **运维信号与干预信号分离。** `run_events` 绝不写进 `interventions`，否则运维告警会吃掉 `daily_cap` 配额与 `cooldown`，并污染 `outcomes` 的效果分析。
3. **不新增窗口内容的持久化。** 漏判明细按需回查数据源，不抄一份存起来（§5.3）。
4. **不重造采集能力。** 回放器合成数据仅用于测试，真实数据始终来自 Screenpipe。

## 5. 观测层

### 5.1 数据来源

| 视图 | 来源 | 需解析 JSON | 新增存储 |
|---|---|---|---|
| 0 概览 / 运行连续性 | `evaluations.at` + `run_events` | 否 | §7 的 `run_events` |
| 1 判定面 | `state` / `data_status` / `skipped` / `late_night` | 否 | 否 |
| 2 闸门面 · 占比分布 | `ent_ratio` / `ent_minutes` / `total_active_minutes` | 否 | 否 |
| 2 闸门面 · 谁挡的 | `gate_trace` | **是** | 否 |
| 3 干预面 | `interventions.*` | 否 | 否 |
| 4 效果面 | `outcomes.*` × `interventions.user_response` | 否 | 否 |
| 5 漏判（一级） | `evaluations.*` | 否 | 否 |
| 5 漏判（二级） | 回查 Screenpipe | 否 | 否 |

`gate_trace` 的实际结构：

```json
[{"name": "state_min", "passed": true, "value": 1.0, "threshold": 1.0}, ...]
```

`value` 可为 `null`，语义是"这个概念此刻不适用"（例如从未干预过，就没有"距上次多少分钟"），**不是**用 `inf` 之类的哨兵值假装它是个数。

`ratio_min` 校准所需的分布**不碰 JSON** —— `ent_ratio` 本身就是独立列。

### 5.2 视图定义

#### 视图 0 · 概览 + 运行连续性

| 输出 | 说明 |
|---|---|
| 区间 | `[first_at, last_at]` |
| 评估轮数 | 行数 |
| 覆盖率 | `轮数 × evaluate_every_minutes / 区间分钟数` |
| **缺口列表** | 相邻 `at` 间隔 > `report.gap_threshold_minutes` 的区间：起、止、分钟数、同期 `run_events` 记录 |
| 结论 | 「数据可信」/「有过 N 处中断」 |

**这是 report 默认输出的第一屏。** 缺口列表是这一版的核心产物 —— 它把 §1.3 的二义性问题变成一个确定结论。

#### 视图 1 · 判定面

- 四状态分布（计数 + 占比），**且区分 `skipped=1` 的行**
- `data_status` 分布
- `late_night` 计数
- `skipped` 行占比**单独高亮** —— 它高就说明"看起来正常"是假的

#### 视图 2 · 闸门面

- 各闸门阻挡次数（解析 `gate_trace`，取第一个 `passed=False` 的闸门）
- `ent_ratio` 分布直方图（分桶 `[0,0.1) … [0.9,1.0]`），仅统计 `total_active_minutes > 0` 的行
- **关键子视图**：`state_min` 通过、但被后续闸门挡住的轮次 —— 这些才是"该提醒但没提醒"的候选，是闸门校准的主要对象。直接打印 `value` vs `threshold`
- `ratio_min` 达标与被挡的对照计数

#### 视图 3 · 干预面

- 触发次数（总计 + 按天）
- 动作分布（`action_id`）
- 触发时的状态分布
- `cooldown` 阻挡次数、`daily_cap` 触达次数
- `delivery_status` 分布
- `user_response` 分布

#### 视图 4 · 效果面

- `outcome` 分布（`disengaged` / `partial` / `continued` / `no_data`）
- **按 `user_response` 分层**：`accepted` / `declined` / `NULL` × `outcome`
- `no_data` 占比
- `ent_before` / `ent_after` 的均值与中位数（仅非 `no_data` 行）

**分层是 V0 规格 §16 风险 6 写明要做、但当前没有任何地方能执行的那件事** —— 风险 6 说"行为回执把『离开电脑』也算作 `disengaged`，分析时应先按 `user_response` 分层"。V0.5 把这条缓解措施落地。

#### 视图 5 · 漏判（两级）

**一级 · 离线可做，零新增存储**

从 `evaluations` 找**漏判锚点**：

```
unclassified_minutes = total_active_minutes - (ent_minutes + gray_minutes + work_minutes)
锚点条件： total_active_minutes          >= report.leak_min_active_minutes
      且 unclassified_minutes / total  >= report.leak_min_unclassified_ratio
```

输出：时刻、`total`、`ent` / `gray` / `work`、`unclassified` 及其占比。

**为什么用 `total_active_minutes` 而不是条目之和**：`total_active_minutes` 是 Screenpipe 自报的活跃量，`ent` / `gray` / `work` 是条目求和。两者不等时，差额既可能是"OTHER 类条目"，也可能是"Screenpipe 报了活跃但没给明细"（V0 已对后者记警告）。

为消除这个混淆，**`evaluations` 新增 `entries_minutes` 列**（条目分钟数之和）。于是：

```
entries_minutes - (ent + gray + work)   → OTHER 类条目，即真正的漏判
total_active_minutes - entries_minutes  → 明细缺失，不是漏判
```

不加这一列，视图 5 就会把两种成因混在一起 —— 而这正是本版本存在的意义所在。

**二级 · 按需回查（`--from-screenpipe`）**

对每个锚点，用**现有的 `ActivityReader`** 重查 `[at - window, at]`，列出未命中任何规则的条目的 `app` / `title` / `minutes`，按分钟降序取前 `report.leak_top_n` 条。

**为什么回查而不是落库**：Screenpipe 本来就是那份数据的 owner，且默认留存 14 天。我们是"按需去查"，不是"抄一份存起来"。这同时满足 V0 规格 §4.4 的数据最小化与"不替换或重造 Screenpipe 的采集能力"。

**已知时效边界**：二级视图受 Screenpipe 留存期限制，超过留存即查不到。一级锚点永久可查，因此漏判的历史记录不会丢失 —— 只是明细会过期。

#### 轨迹视图 · `--trace <时刻>`

以给定时刻为中心，按时间顺序打印每轮评估：`at`、`state`、`ent_ratio`、`ent_minutes` / `total_active_minutes`、逐条闸门 `(name, value, threshold, passed)`、`decision`、`skipped`。

**这是判断"20 / 40 / 65 阶梯合不合理"唯一能看的形态** —— 其余视图都是聚合的，看不到过程。

### 5.3 与数据最小化的关系

V0 规格 §4.4 的三条边界原则在 V0.5 全部保持：

| 原则 | V0.5 如何保持 |
|---|---|
| 不消费屏幕文本 | 回查只取 `app_name` / `window_name` / `browser_url` / `minutes`，`include_*` 四个参数照旧全关 |
| 不替换或重造采集能力 | 二级视图回查 Screenpipe 本身，不自建历史 |
| 数据最小化 | **不新增任何窗口内容的持久化**；唯一新增的 `entries_minutes` 是聚合数，不含标题 |

**窗口标题落在哪里**：仅落在 report 的 stdout 上，供人当场阅读，**不写库**。这是刻意的 —— 想看的时候能看，不该留的不留。

### 5.4 输出形态

| 形态 | 用途 |
|---|---|
| `text`（默认） | 对齐表格，直接给人读 |
| `json` | 给 `jq` 与后续分析用 |

**默认输出只给概览 + 一句话结论 + 缺口列表**，其余视图需要 `--views` 显式指定。理由：一次输出六个视图的表，人不会看第二遍。

## 6. 回放器

### 6.1 落点与职责

```
src/statesense/replay/
├─ scenario.py     # 剧本模型：时间线 + 每段活动
├─ synthesize.py   # 剧本 + 虚拟时刻 + 窗口 → ActivitySnapshot
├─ runner.py       # FrozenClock + 脚本 reader + 真实 Scheduler + 临时 DB
└─ scenarios.py    # 五个内置剧本及其期望断言
```

### 6.2 剧本模型

一个剧本 = 若干段，每段声明：

| 字段 | 含义 |
|---|---|
| `offset_minutes` | 距剧本起点的偏移 |
| `duration_minutes` | 持续时长 |
| `app` / `title` / `url` | 活动元数据 |

**`data_status` 是剧本级属性，不是段级属性。** 理由：它描述的是"这一轮取数据的结果"，属于快照整体；`degraded` 剧本要造的是"整个窗口都取不到"，把它挂在某一段上会产生语义不明（同一快照里两段各自声称不同的 `data_status`）。剧本级默认 `ok`，`degraded` 剧本整体覆盖为 `unreachable`。

`synthesize.py` 在任意虚拟时刻 `now`，把落在 `[now - window, now]` 内的段裁剪成 `Entry`，构造 `ActivitySnapshot`。**这就是真实 `ActivityReader` 返回的东西的形状**，回放器不发明新结构。

### 6.3 驱动真实的 `Scheduler`

**这是本节最重要的设计决定。**

回放器不重跑判定逻辑，而是注入 `FrozenClock` + 脚本 reader + 真实 `Scheduler` + 临时 DB。于是被验证的是**生产链路本身**（含 store 写入、闸门求值、动作轮转、回执落行），而不是一个会与生产漂移的平行复刻品。

### 6.4 五个剧本

| 剧本 | 造什么 | 验什么 | 对应来源 |
|---|---|---|---|
| `ladder` | 连续 90 分钟娱乐 | 20/40/65 真的产生 `WATCH → PASSIVE_CONSUMPTION → HIGH_RISK_PASSIVE_CONSUMPTION`，且在 `PASSIVE_CONSUMPTION` 处触发干预 | 验证日志 §7 第 1 条**未验证** |
| `outcome` | 触发后行为继续 / 停止两种走向 | T+10min 真的落 `outcomes` 行，且标签符合 `disengaged_ratio` / `continued_ratio` | §7 第 2 条**未验证** |
| `gates` | cooldown 29 vs 31 分钟；当天第 8 次 vs 第 9 次 | 边界值精确，不多不少 | 审查发现·闸门静默失效 |
| `degraded` | `data_status = unreachable` | 落 `skipped=1`，且**不**判成 `NORMAL` | 审查发现·最严重之二 |
| `sleep_gap` | 制造 > 2×窗口的空档 | 跳过本轮评估 + `run_events` 落行 | 本版新增的健康信号（§7） |

**`gates` 与 `degraded` 是其中最有价值的两个。** V0 的那两条最严重问题都是"154 个测试全绿之后才被发现"的 —— 它们不靠单元测试暴露，靠配置组合与真实数据暴露。回放器把它们变成回归用例，**让它们不可能再悄悄回来**。

### 6.5 `ActivitySource` 缝隙

`Scheduler.__init__` 目前写的是具体类 `reader: ActivityReader`，而 `Clock` 与 `Notifier` 都是 Protocol。新增 `activity/base.py` 的 `ActivitySource` Protocol（方法签名与 `ActivityReader.read` 一致），把"唯一可替换的数据源缝隙"在代码里立起来。

> **如实标注**：本仓库没有配置类型检查器（`pyproject.toml` 只有 `[tool.pytest.ini_options]`）。因此这个改动**不是为了静态检查通过**，纯粹是为了把缝隙写进代码、让回放器有据可依。收益真实但有限，不是架构升级。

### 6.6 能验证什么，不能验证什么

| | 项 |
|---|---|
| ✅ 能验**机制** | 20/40/65 阶梯真的会触发；闸门组合真的按预期挡或放；T+10min 回执真的落 `outcomes`；跨天、跨 cooldown、`daily_cap` 边界；降级数据真的不误判 |
| ❌ 不能验**时机好不好** | 合成数据是人编的，不代表真实分布 |
| ❌ 不能验**分类清单准不准** | 同上 |
| ❌ 不能验**弹窗是否真的可见** | 需真实桌面环境，V0 已手工验证 |

**回放器把"需要等"变成"不需要等"，但不能把"需要真实使用"变成"不需要真实使用"。**

### 6.7 与 report 的配合

`--replay <剧本> --keep-db` 保留临时库，随后可用 `--report --db <该库>` 阅读它 —— 回放产出数据，report 消费数据，形成一条**不依赖真实时间**的完整验证回路。

## 7. 健康信号

### 7.1 为什么不需要心跳表

`ActivityReader.read()` 永不抛异常（§1.3）：采集侧的所有故障都会变成 `data_status` 的一个取值并**落行**。`evaluations.data_status` 已经是一份逐 tick 的完整断连日志。

因此 V0.5 不新增心跳表，只补齐 §1.3 表格里的 (a) 与 (c) 两种情况。

### 7.2 `run_events` 表

```sql
CREATE TABLE IF NOT EXISTS run_events (
  at     TEXT PRIMARY KEY,
  kind   TEXT NOT NULL,   -- 封闭枚举：'sleep_gap' | 'tick_error'
  detail TEXT NOT NULL    -- sleep_gap: 空档分钟数；tick_error: 异常类名 + 消息首行（截断至 200 字符）
);
```

只记录**异常**，不记录正常 tick —— 正常存活由 `evaluations.at` 派生。避免同一事实存两遍（与 V0 "`state_transitions` 由 `evaluations` 派生"同一原则）。

### 7.3 两处补丁

| 位置 | 现状 | 改为 |
|---|---|---|
| `scheduler.py:111` 休眠/唤醒提前 return | 静默跳过，不落行 | 一并写 `run_events(kind='sleep_gap', detail=空档分钟数)` |
| `run_forever` 的 `except Exception` | 只 `log.exception`，不落库 | 一并写 `run_events(kind='tick_error', detail=异常类名+消息首行)` |

### 7.4 三态判定

补完之后，"没有记录"这个现象**从二义变确定**：

| 看到什么 | 结论 |
|---|---|
| 有 `evaluations` 行 | 正常跑了 |
| 无行 + 有 `run_events` 行 | 有意跳过 / 出错（**可辨**） |
| 无行 + 无 `run_events` | **进程死了**（唯一解释） |

判定"此刻是否掉线"：`now - max(evaluations.at) > report.gap_threshold_minutes`。

### 7.5 两条硬约束

1. **`run_events` 绝不写进 `interventions`。** 否则运维告警会占用 `daily_cap` 配额、消耗 `cooldown`，并在 `outcomes` 里混进一堆不是干预的"干预效果"数据，使视图 4 的分层分析当场失效。
2. **健康告警绝不弹窗。** 告警的落点是 report 的视图（事后可判）。进程的自动恢复交给任务计划程序的"失败后重启"设置 —— 属部署配置，不是代码。

### 7.6 已知边界

若 `Store` 自身失效（磁盘满、库损坏），`run_events` 也写不进去，此时退化为"看起来像进程死了"。这是可接受的降级，但**必须写明** —— 否则将来会把一次磁盘故障误判成进程崩溃。

## 9. 数据模型变更（schema v3 → v4）

| 变更 | 内容 | 理由 |
|---|---|---|
| 新增表 | `run_events(at, kind, detail)` | §7.2 |
| 新增列 | `evaluations.entries_minutes REAL NOT NULL DEFAULT 0` | 区分"OTHER 类条目"与"明细缺失"，使视图 5 的锚点精确（§5.2） |

迁移沿用 `_apply_incremental_migrations()` 的既有机制，`SCHEMA_VERSION` 递增到 4。

`entries_minutes` 需在 `StateVerdict` 上新增同名字段（条目 `minutes` 之和），由 `engine` 计算 —— 与 `ent_minutes` / `gray_minutes` / `work_minutes` 同一处产出，保证口径一致。

**该 Python 字段刻意不给默认值。** `ent_minutes` / `gray_minutes` / `work_minutes` 三个同类字段都没有默认值；而 `0.0` 在这里恰好是"条目明细缺失"这个可疑信号本身 —— 给默认值等于让漏掉它的构造点静默产生假信号，使真正该被发现的漏判反而不触发锚点。全仓仅 7 处构造点（2 处在 `engine` 的共享 dict 内，5 处在测试 helper）。

> 与上表 SQL 列的 `DEFAULT 0` 不矛盾：那是给**旧行**读取用的兼容值（迁移层），这里说的是**新代码构造 `StateVerdict` 时**是否允许省略（契约层）。两件事。

**旧库兼容**：`DEFAULT 0` 使既有行可读；对旧行，视图 5 的锚点判据退化为使用 `total_active_minutes`，并在输出中标注"该区间无 `entries_minutes` 记录"。不伪造数据。

## 10. 配置变更

新增一节：

```toml
[report]
# 连续性阈值，同时用于两个判定（两者语义不同但阈值相同，故不设两个键）：
#   · 回看历史：相邻评估的间隔超过它 → 记为一处缺口
#   · 判断当下：最后一条评估距今超过它 → 视为掉线
# 默认 = 3 × schedule.evaluate_every_minutes
gap_threshold_minutes = 15
# 漏判锚点：窗口活跃至少这么多分钟
leak_min_active_minutes = 30
# 漏判锚点：未归类占比至少这么高
leak_min_unclassified_ratio = 0.7
# 二级漏判视图最多列几条明细
leak_top_n = 10
```

沿用 V0 的启动即校验：`gap_threshold_minutes` 必须为正；`leak_min_unclassified_ratio` 必须落在 `(0, 1]`。**非法值启动即失败，不静默降级。**

## 11. CLI 变更

```
statesense --check                          （V0）
statesense --once [--dry-run]               （V0）
statesense --daemon                         （V0）
statesense --report [--since 7d] [--format text|json]
                    [--views all|0,1,2,3,4,5] [--trace <ISO 时刻>] [--from-screenpipe]
statesense --replay <ladder|outcome|gates|degraded|sleep_gap|all> [--keep-db]
```

| 决策 | 理由 |
|---|---|
| `--report` / `--replay` 加入既有的互斥组 | 与 `--check` / `--once` / `--daemon` 同级，保持"一次只做一件事" |
| `--replay` 默认写临时库，跑完删除 | 绝不污染生产库 |
| `--replay all` | 直接服务 §2 判据 1 |
| `--report` 默认不带 `--from-screenpipe` | 离线可读；回查 Screenpipe 是显式动作 |

**`--report` 是只读命令**：不构造任何写入语句。`Store` 新增的方法一律以 `fetch_` / `list_` / `count_` 开头，便于评审时一眼确认。

## 12. 错误与边界

| 情形 | 行为 |
|---|---|
| `--report` 时库不存在 | 明确报错并提示先跑 `--once` 或 `--daemon`，退出码 2 |
| `--report` 时库为空（零行） | 正常输出"区间内无任何评估记录"，**不是错误**（这正是"进程从未跑起来"的观测结果） |
| `--from-screenpipe` 但 API key 缺失 | 仅二级视图跳过并提示，一级视图照常输出；退出码 0 |
| `--from-screenpipe` 但 Screenpipe 不可达 | 同上，并在输出中标注"明细不可用" |
| `gate_trace` 解析失败 | 该行计入"闸门数据损坏"计数并跳过，不中断整份报告 |
| `--replay` 指定未知剧本名 | 列出可用剧本，退出码 2 |
| `--replay` 剧本断言失败 | 打印期望 vs 实际，退出码 1 |
| 旧库缺 `entries_minutes` 列 | 迁移自动补列；历史行按 §9 的降级方式处理 |
