# StateSense-Agent V0.5 技术规格：可验证与可观测

> 状态：**待评审**
> 前置：V0（`docs/specs/2026-09-16-v0-state-intervention-design.md`，已合并）
> 本规格不修改 V0 的判定逻辑、闸门语义与投递通道。

---

## 1. 背景与问题

V0 已交付：采集 → 判定 → 闸门 → 动作 → 投递 → 双轨回执 → 存储的完整链路，154 个测试全绿。

但 V0 留下一个不对称：

| | 定义 | V0 现状 |
|---|---|---|
| **测（test）** | 给定输入 → 期望输出，可重复、可断言 | 154 个，6.6 秒 |
| **观测（observe）** | 真实运行中发生了什么，不可重复，只能记录 + 回看 | **写入完整，读出为零** |

"读出为零"的具体含义：`Store` 的公开方法全是写入与运行时判定用的（`insert_*` / `fetch_*` / `due_interventions` / `last_intervention_at` / `intervention_count_since`），**没有一个是给人看的聚合查询**；CLI 只有 `--check`（当下快照）/ `--once`（一行）/ `--daemon`。**没有任何命令能回答"过去三天发生了什么"。**

### 1.1 三个未验证项

V0 验证日志 §7 的诚实清单：

| 项 | 状态 | 未验证的原因 |
|---|---|---|
| 真实长时段被动消费触发干预 | 未验证 | 需要真实刷 40+ 分钟 |
| T+10min 行为回执实际落行 | 未验证 | 同上 |
| `--daemon` 与任务计划程序注册 | 未验证 | 属部署动作 |

**关键判断：前两项之所以未验证，只是因为它们需要"等"，不是因为难测。** 它们的触发条件是时间的流逝，而不是输入的组合 —— 而这可以用注入时钟 + 注入数据源在秒级内复现。

### 1.2 一个数据可信度问题

`evaluations` 只存聚合分钟数（`ent` / `gray` / `work`），**不存窗口条目**。而分类清单 100% 由配置驱动，代码里没有内置默认（`config.py:180` 只校验 `entertainment` 非空）。

实测后果（验证日志 §10.1）：

```
取到 24 条窗口记录，总活跃 59.9 分钟
    46.9 分钟  Brotato          ← 游戏，被判成 NORMAL
state=NORMAL  intervened=False  note=ratio_min 未通过（0.04 vs 阈值 0.75）
```

刷了 47 分钟游戏，`ent = 0`，系统判定 `NORMAL`。

**并且实际的 `config/config.toml` 与 `config/config.example.toml` 逐字节相同** —— 分类清单从未按本人配置过。清单里放的是平台名（`steam`、`epic games`、`battle\.net`、`wegame`），而 Steam 启动的游戏，进程名与窗口标题都是游戏自身，不含平台关键词。

**这卡在 V0.5 的要害上**：`ratio = ent / total_active`。若真实数据里游戏占大头，用这份数据校准 `ratio_min` 就是在**用一份系统性漏掉最强娱乐信号的数据**做决定。

### 1.3 一个二义性

`ActivityReader.read()` **永不抛异常** —— 任何异常、非 200、JSON 坏掉、`data_status` 不认识，全部走 `_degraded()` 返回 `data_status='unreachable'` 的快照，而 `_evaluate_tick` 对每一轮都调 `insert_evaluation`。

**所以 `evaluations.data_status` 已经是一份逐 tick 的完整断连日志。健康信号不需要心跳表。**

但只有三种情况**不落行**，而它们在库里完全无法区分：

| # | 情况 | 代码位置 | 结果 |
|---|---|---|---|
| a | 休眠/唤醒空档 > 2×窗口 | `scheduler.py:111` 提前 return | 不落行（**有意跳过**） |
| b | 进程根本没在跑 / 死了 | —— | 不落行 |
| c | tick 内抛异常 | `run_forever` 的 `except Exception` | **只写日志，不落库** |

跑 5 天中间断了 6 小时，report 只能说"有 6 小时没记录"，无法回答是合盖睡了、进程崩了、还是崩在日志里了。

## 2. 成功判据

V0.5 只回答一个问题：

> **V0 到底在不在跑，跑出来的数据能不能用？**

具体判据，逐条可证伪：

| # | 判据 | 证伪方式 |
|---|---|---|
| 1 | 五个回放剧本全过，其中 `ladder` 与 `outcome` 把 §1.1 的前两条从未验证变为已验证 | 任一剧本失败 |
| 2 | `--report` 能回答四个问题：它在跑吗 / 为什么没提醒我 / 提醒了几次 / 有用吗 | 任一问题答不上 |
| 3 | 挂常驻跑满 5 天，report 的缺口视图与实际睡眠、重启记录对得上 | 缺口无解释或解释错误 |
| 4 | `ratio_min` 做出一个**有依据**的判断（调或不调均可，但必须有 `ent_ratio` 分布支撑） | 无数据支撑就下结论 |
| 5 | 现有 154 个测试不退化 | 任一失败 |

**第 4 条是刻意的：V0.5 不承诺"把 0.75 改成某个更好的数"。** 承诺改数值，等于把一个必须由数据回答的问题在规格里偷偷写死。

## 3. 非目标

- ~~**不做自动分类推断。**~~ **已修订（2026-09-17）：只开一条口子。**
  原文的理由是"四个候选方向没有一个是干净的"。实施阶段找到了第五条路，它绕开了那四个方向的问题：**`SHQueryUserNotificationState`** —— Windows 自己用来判断"现在该不该弹通知"的调用，**不需要任何游戏清单、不引入依赖、不重造采集能力**。因此允许这**唯一一处**自动推断，规则与代价见 §4.5。
  其余仍不做：外部进程映射表、全屏几何启发式、以及任何形式的"猜游戏名"。
- **不改判定逻辑、闸门语义、投递通道。** 这些属 V0 契约。§9 新增的 `entries_minutes` 是**派生字段**，只用于观测，**不参与 `classify` 与任何闸门判定**。`fullscreen_state`（§4.5）**是**判定输入，但只影响 `ent` 的构成，闸门语义与投递通道不动。
- **不做实时告警通道。** 见 §7.5。
- **不引入 LLM**，`Wording` 接口保持原样。
- **不新增窗口内容的持久化。** 见 §5.3。
- **不做 V1 的"什么干预最有效"分析。** V0.5 只把所需数据变得可读。

## 4. 架构

### 4.1 分层

```
┌──────────────────────────────────────────────┐
│ __main__.py                                  │
│   --check / --once / --daemon    （V0）      │
│   --report / --replay            （V0.5 新增）│
└────────────┬─────────────────────────────────┘
             │
     ┌───────┴────────┬──────────────┐
     ▼                ▼              ▼
┌─────────┐   ┌─────────────┐  ┌──────────┐
│ report/ │   │  replay/    │  │scheduler │
│ 聚合+渲染│   │ 剧本+驱动    │  │  （V0）  │
│ （纯函数）│   │             │  │          │
└────┬────┘   └──────┬──────┘  └────┬─────┘
     │               │              │
     ▼               ▼              ▼
┌──────────────────────────────────────────────┐
│ store/   只读查询（V0.5 新增）+ 写入（V0）    │
└──────────────────────────────────────────────┘
```

`report/` 与 `replay/` **都只透过 `store/` 与既有接口访问数据**，不直接写 SQL、不绕过 `Store`。

### 4.2 组件职责边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| `store/db.py` | 拥有 SQL 与 schema 知识；提供**只读查询方法**返回原始行 | 聚合、渲染、判断 |
| `report/` | 聚合（纯函数）+ 渲染（纯函数） | SQL、网络、写库 |
| `replay/` | 剧本模型 + 合成快照 + 驱动 `Scheduler` | 重新实现判定逻辑 |
| `activity/base.py` | `ActivitySource` Protocol | 任何实现 |
| `scheduler.py` | tick 主循环（V0）；V0.5 只补 `run_events` 落行 | 观测 |

**分工原则：`Store` 交出"行"，`report/` 交出"意思"。** 聚合逻辑是纯函数，因此能被现有的测试体系覆盖，不需要数据库或网络。

### 4.3 一次 `--report` 的数据流

```
config.toml ──► Store（只读查询）──► rows ──► report 聚合（纯函数）
                                                  │
                            ┌─────────────────────┤
                            ▼                     ▼
                      text 渲染              json 渲染
                            │
                            └──► stdout（绝不写库）

可选：--from-screenpipe ──► ActivityReader ──► Screenpipe（只读回查）
```

### 4.4 五条边界原则

1. **report 只读。** 绝不写库 —— 避免"看数据把数据看了坏"。实现上由 `Store` 的只读方法与"report 不构造写入语句"共同保证。
2. **运维信号与干预信号分离。** `run_events` 绝不写进 `interventions`，否则运维告警会吃掉 `daily_cap` 配额与 `cooldown`，并污染 `outcomes` 的效果分析。
3. **不新增窗口内容的持久化。** 漏判明细按需回查数据源，不抄一份存起来（§5.3）。
4. **不重造采集能力。** 回放器合成数据仅用于测试，真实数据始终来自 Screenpipe。**例外**：§4.5 的全屏信号是一次本地 Win32 调用，它不采集内容、不替代 Screenpipe —— Screenpipe 的 `activity-summary` 里根本没有"是否全屏"这个信息，只能向系统直接问。
5. **唯一一处自动推断必须可审计。** §4.5 的全屏信号逐轮记原始值（不是布尔），否则事后无法回答"它当时看到了什么、准不准"。

### 4.5 全屏信号：唯一一处自动推断

**要解决的问题。** 游戏窗口的标题与进程名就是游戏自身（实测 `Brotato.exe` / `Brotato`、`DeltaForceClient-Win64-Shipping.exe` / `三角洲行动`），配置里的平台名（`steam` / `wegame`）抓不到它。按游戏名逐个维护清单没有普适性：换一个游戏就漏一次。

**为什么不能识别后台的游戏平台。** Screenpipe 是屏幕采集，只"看见"屏幕上的东西。没有可见窗口的后台进程不产生任何帧 —— 历史数据里 Steam 主进程 `steam.exe` 从未出现过，只有画窗口的 `steamwebhelper.exe`。**"识别后台的 Steam/WeGame"在现有数据源下做不到。** 而且逻辑上也不成立：两者都是常驻托盘的，"平台在运行" ≠ "在玩游戏"。

**采用的信号。** `SHQueryUserNotificationState()`（shell32，纯 ctypes，0 依赖）—— Windows 自己用它决定"现在该不该弹通知"，语义正是"有没有全屏应用在跑"。

**判定规则：**

```
fullscreen_state ∈ {2, 3} 且 snapshot 可信  →  把未命中任何规则的条目（OTHER）计入 ent
```

- 只提权 `OTHER`，**不动 `WORK` / `GRAY`** —— 边打游戏边开终端时，终端时间不该算娱乐。
- 数据不可信时不提权：那时连 `ent` 本身都不该有结论。

**为什么是 {2, 3} 而不是只取 3。** 原设计只取 `QUNS_RUNNING_D3D_FULL_SCREEN`(3)，理由是 `QUNS_BUSY`(2) 还包含演示模式与全屏文档，看起来更安全。**本机实测推翻了它**：三角洲行动在前台时连采 6 次全返回 **2**，从未返回 3。只取 3 等于这条信号在本机永远不触发。无边框窗口模式的游戏似乎都落在 2。

**接受 2 的代价，由三件事兜住：**

| 兜底 | 说明 |
|---|---|
| 只提权未归类条目 | 全屏看文档时，若该应用已在 `work` 清单里，时间仍不算娱乐 |
| 时长门槛 | 短暂的全屏文档只贡献几分钟，够不到 `watch_minutes`(20) 门槛 |
| 原始值入库 | `evaluations.fullscreen_state` 记的是 2/3/5/None，不是布尔；误判可事后审计（§5.2 视图 1 给出分布） |

**`None` 与「不是全屏」是两件事**：前者是不知道，后者是知道。非 Windows、调用失败、返回枚举外的值 —— 一律 `None`，一律不提权。绝不把"不知道"当成"不是"。

**已知会漏的情况**：无边框窗口模式下若系统返回 5 而非 2/3，这条信号就看不到 —— 但那种情况下 §8 的游戏名清单仍然有效，两条腿互补。

## 5. 观测层

### 5.1 数据来源

| 视图 | 来源 | 需解析 JSON | 新增存储 |
|---|---|---|---|
| 0 概览 / 运行连续性 | `evaluations.at` + `run_events` | 否 | §7 的 `run_events` |
| 1 判定面 | `state` / `data_status` / `skipped` / `late_night` | 否 | 否 |
| 2 闸门面 · 占比分布 | `ent_ratio` / `ent_minutes` / `total_active_minutes` | 否 | 否 |
| 2 闸门面 · 谁挡的 | `gate_trace` | **是** | 否 |
| 3 干预面 | `interventions.*` | 否 | 否 |
| 4 效果面 | `outcomes.*` × `interventions.user_response` | 否 | 否 |
| 5 漏判（一级） | `evaluations.*` | 否 | 否 |
| 5 漏判（二级） | 回查 Screenpipe | 否 | 否 |

`gate_trace` 的实际结构：

```json
[{"name": "state_min", "passed": true, "value": 1.0, "threshold": 1.0}, ...]
```

`value` 可为 `null`，语义是"这个概念此刻不适用"（例如从未干预过，就没有"距上次多少分钟"），**不是**用 `inf` 之类的哨兵值假装它是个数。

`ratio_min` 校准所需的分布**不碰 JSON** —— `ent_ratio` 本身就是独立列。

### 5.2 视图定义

#### 视图 0 · 概览 + 运行连续性

| 输出 | 说明 |
|---|---|
| 区间 | `[first_at, last_at]` |
| 评估轮数 | 行数 |
| 覆盖率 | `轮数 / 按节奏本该有的轮数`，后者 = `区间跨度 // evaluate_every_minutes + 1` |
| **此刻** | 最后一次评估距今多少分钟、阈值多少、之后有没有 `run_events` —— §7.4 的「判断当下」 |
| **缺口列表** | 相邻 `at` 间隔 > `report.gap_threshold_minutes` 的区间：起、止、分钟数、同期 `run_events` 记录 |
| 结论 | 「数据可信」/「有过 N 处中断」/**「此刻已掉线」**（掉线压过前两者） |

> **覆盖率公式已修订（2026-09-18）。** 原文写的是 `轮数 × evaluate_every_minutes / 区间分钟数`，
> 它在正常满跑时会算出 >100%：span=30、every=5、轮数=7 时是 `1.167`。覆盖率超过 100%
> 只会让人怀疑这个数字本身，所以改成「按节奏本该有多少轮」当分母，值域落在 (0, 1]。
> 这是实现反推规格的一处修订，不是实现偏离规格。

**「此刻」为什么必须出现在这一屏**：缺口列表回答的是「过去断过没有」，答不了
「现在掉线了吗」—— 而后者才是打开报告的人真正想知道的。§10 把这一个配置键设计成
「回看历史」与「判断当下」两用，只实现前一半等于把那个设计丢掉一半。
**这一行还有一个真实用途**：报告是在人已经感觉不对劲时才被打开的，
那时最需要的是一句确定的话，而不是自己从缺口列表里推断。

**这是 report 默认输出的第一屏。** 缺口列表是这一版的核心产物 —— 它把 §1.3 的二义性问题变成一个确定结论。

#### 视图 1 · 判定面

- 四状态分布（计数 + 占比），**且区分 `skipped=1` 的行**
- `data_status` 分布
- **全屏信号原始值的分布**（`2` / `3` / `1,4,5,6,7` / `unknown`）—— 这是 §4.5 那条自动推断唯一的审计入口：只有看见它取过哪些值，"准不准"才有得谈
- `late_night` 计数
- `skipped` 行占比**单独高亮** —— 它高就说明"看起来正常"是假的
- **明细缺失轮数**（`total_active_minutes > 0` 且 `entries_minutes <= 0`）—— 这些轮上视图 5 的两个差额都退化，判据不成立。**不说出口，视图 5 的"没有漏判"就会被读成覆盖了全部轮次。** 迁移前写入的行（`entries_minutes` 取 `DEFAULT 0`）也落在这一档，且在数据上无法与「Screenpipe 真的没返回明细」区分，所以只能一起计数、一起说明

#### 视图 2 · 闸门面

- 各闸门阻挡次数（解析 `gate_trace`，取第一个 `passed=False` 的闸门）
- **各闸门触达次数**（统计每一个 `passed=False` 的闸门）—— 一轮可以同时被 `cooldown` 与 `daily_cap` 挡下，只统计第一个会把 `daily_cap` 的触达次数少算，从而把一个恰好触及上限的日子读成"没到上限"
- `ent_ratio` 分布直方图（分桶 `[0,0.1) … [0.9,1.0]`），仅统计 `total_active_minutes > 0` 的行
- **关键子视图**：`state_min` 通过、但被后续闸门挡住的轮次 —— 这些才是"该提醒但没提醒"的候选，是闸门校准的主要对象。直接打印 `value` vs `threshold`
- `ratio_min` 达标与被挡的对照计数
- **闸门数据损坏轮数** —— 这些行已从上面的全部统计中剔除，不报出来就会被读成"闸门没挡过"

#### 视图 3 · 干预面

- 触发次数（总计 + 按天）
- 动作分布（`action_id`）
- 触发时的状态分布
- **投递通道分布**（`foreground_popup` / `recording`）—— `--dry-run` 走 `RecordingNotifier`，它同样返回 `delivered`；不记通道，排练出来的干预与真实干预在库里完全一样，"到底有没有真的弹过窗"将永远答不上来。**这一项是 `interventions.channel` 列存在的全部理由**（§9）
- `cooldown` 阻挡次数、`daily_cap` 触达次数（取自 §5.2 视图 2 的「各闸门触达」，不重算）
- `delivery_status` 分布
- `user_response` 分布

> **`user_response` 为 NULL 的那一层在输出里叫 `null`。** 不叫 `none`、不叫 `unknown`：
> 报告的使用者要能把这一行直接对回自己的 SQL 查询，中间多一层翻译就多一次出错机会。
> 找不到对应干预行的孤儿回执另记一层 `orphan` —— 那是**数据不完整**，不是"用户没回应"，
> 混为一谈会让分层分析悄悄少算一层。

#### 视图 4 · 效果面

- `outcome` 分布（`disengaged` / `partial` / `continued` / `no_data`）
- **按 `user_response` 分层**：`accepted` / `declined` / `NULL` × `outcome`
- `no_data` 占比
- `ent_before` / `ent_after` 的均值与中位数（仅非 `no_data` 行）

**分层是 V0 规格 §16 风险 6 写明要做、但当前没有任何地方能执行的那件事** —— 风险 6 说"行为回执把『离开电脑』也算作 `disengaged`，分析时应先按 `user_response` 分层"。V0.5 把这条缓解措施落地。

#### 视图 5 · 漏判（两级）

**一级 · 离线可做，零新增存储**

从 `evaluations` 找**漏判锚点**：

```
unclassified_minutes = total_active_minutes - (ent_minutes + gray_minutes + work_minutes)
锚点条件： total_active_minutes          >= report.leak_min_active_minutes
      且 unclassified_minutes / total  >= report.leak_min_unclassified_ratio
```

输出：时刻、`total`、`ent` / `gray` / `work`、`unclassified` 及其占比。

**为什么用 `total_active_minutes` 而不是条目之和**：`total_active_minutes` 是 Screenpipe 自报的活跃量，`ent` / `gray` / `work` 是条目求和。两者不等时，差额既可能是"OTHER 类条目"，也可能是"Screenpipe 报了活跃但没给明细"（V0 已对后者记警告）。

为消除这个混淆，**`evaluations` 新增 `entries_minutes` 列**（条目分钟数之和）。于是：

```
entries_minutes - (ent + gray + work)   → OTHER 类条目，即真正的漏判
total_active_minutes - entries_minutes  → 明细缺失，不是漏判
```

不加这一列，视图 5 就会把两种成因混在一起 —— 而这正是本版本存在的意义所在。

**二级 · 按需回查（`--from-screenpipe`）**

对每个锚点，用**现有的 `ActivityReader`** 重查 `[at - window, at]`，列出未命中任何规则的条目的 `app` / `title` / `minutes`，按分钟降序取前 `report.leak_top_n` 条。

**没有锚点也要说一句话。** 用户正是**因为**看不到明细才加的 `--from-screenpipe`；
「没锚点所以什么都不打印」会让他以为参数没生效，或者以为回查坏了。
同理，API key 缺失时的提示也不能因为「没有锚点」而被跳过（§12）。

**为什么回查而不是落库**：Screenpipe 本来就是那份数据的 owner，且默认留存 14 天。我们是"按需去查"，不是"抄一份存起来"。这同时满足 V0 规格 §4.4 的数据最小化与"不替换或重造 Screenpipe 的采集能力"。

**已知时效边界**：二级视图受 Screenpipe 留存期限制，超过留存即查不到。一级锚点永久可查，因此漏判的历史记录不会丢失 —— 只是明细会过期。

#### 轨迹视图 · `--trace <时刻>`

以给定时刻为中心，按时间顺序打印每轮评估：`at`、`state`、`ent_ratio`、`ent_minutes` / `total_active_minutes`、逐条闸门 `(name, value, threshold, passed)`、`decision`、`skipped`。

**这是判断"20 / 40 / 65 阶梯合不合理"唯一能看的形态** —— 其余视图都是聚合的，看不到过程。

> **「以给定时刻为中心」是刻意的（2026-09-18 修订说明）。** 原实现取的是
> 「`at` 及它之前最近的 12 轮」，即 `at` 落在末尾。那样一来「判完之后又怎样了」
> 永远看不到，而这恰恰是复盘一次干预最想知道的部分。现在改为左半取 `at` 之前
> （含最近一轮）、右半取之后；窗口为偶数时取舍偏向过去，因为「为什么这么判」的
> 证据在左边。`at` 早于全部记录时从最早一轮开始给，而不是给空 —— 空输出会被读成
> 「工具坏了」，而实际情况是「那时候还没有数据」，两者不是一回事。

### 5.3 与数据最小化的关系

V0 规格 §4.4 的三条边界原则在 V0.5 全部保持：

| 原则 | V0.5 如何保持 |
|---|---|
| 不消费屏幕文本 | 回查只取 `app_name` / `window_name` / `browser_url` / `minutes`，`include_*` 四个参数照旧全关 |
| 不替换或重造采集能力 | 二级视图回查 Screenpipe 本身，不自建历史 |
| 数据最小化 | **不新增任何窗口内容的持久化**；唯一新增的 `entries_minutes` 是聚合数，不含标题 |

**窗口标题落在哪里**：仅落在 report 的 stdout 上，供人当场阅读，**不写库**。这是刻意的 —— 想看的时候能看，不该留的不留。

### 5.4 输出形态

| 形态 | 用途 |
|---|---|
| `text`（默认） | 对齐表格，直接给人读 |
| `json` | 给 `jq` 与后续分析用 |

**默认输出只给概览 + 一句话结论 + 缺口列表**，其余视图需要 `--views` 显式指定。理由：一次输出六个视图的表，人不会看第二遍。

## 6. 回放器

### 6.1 落点与职责

```
src/statesense/replay/
├─ scenario.py     # 剧本模型：时间线 + 每段活动 + 该剧本的全屏信号
├─ synthesize.py   # 剧本 + 虚拟时刻 + 窗口 → ActivitySnapshot
├─ runner.py       # FrozenClock + 脚本 reader + 脚本探针 + 真实 Scheduler + 临时 DB
└─ scenarios.py    # 五个内置剧本及其期望断言
```

**每一个外部输入都必须由剧本给定。** 时间用 `FrozenClock`、活动数据用 `ScriptedReader`、
全屏信号用 `ScriptedFullscreenProbe`。漏掉任何一个，`Scheduler` 就会退到真实环境的默认实现 ——
而那正是这套工具存在的理由的反面：`run_scenario` 曾经没注入探针，于是同一个
`--replay all` 会因为"跑回放的这一刻我是不是正开着游戏"给出不同结果（§15 风险 13）。

### 6.2 剧本模型

一个剧本 = 若干段，每段声明：

| 字段 | 含义 |
|---|---|
| `offset_minutes` | 距剧本起点的偏移 |
| `duration_minutes` | 持续时长 |
| `app` / `title` / `url` | 活动元数据 |

**`data_status` 是剧本级属性，不是段级属性。** 理由：它描述的是"这一轮取数据的结果"，属于快照整体；`degraded` 剧本要造的是"整个窗口都取不到"，把它挂在某一段上会产生语义不明（同一快照里两段各自声称不同的 `data_status`）。剧本级默认 `ok`，`degraded` 剧本整体覆盖为 `unreachable`。

`synthesize.py` 在任意虚拟时刻 `now`，把落在 `[now - window, now]` 内的段裁剪成 `Entry`，构造 `ActivitySnapshot`。**这就是真实 `ActivityReader` 返回的东西的形状**，回放器不发明新结构。

### 6.3 驱动真实的 `Scheduler`

**这是本节最重要的设计决定。**

回放器不重跑判定逻辑，而是注入 `FrozenClock` + 脚本 reader + 真实 `Scheduler` + 临时 DB。于是被验证的是**生产链路本身**（含 store 写入、闸门求值、动作轮转、回执落行），而不是一个会与生产漂移的平行复刻品。

### 6.4 五个剧本

| 剧本 | 造什么 | 验什么 | 对应来源 |
|---|---|---|---|
| `ladder` | 连续 90 分钟娱乐 | 三档阈值真的产生 `WATCH → PASSIVE_CONSUMPTION → HIGH_RISK_PASSIVE_CONSUMPTION`，且在 `PASSIVE_CONSUMPTION` 处触发干预；并额外断言 `HIGH_RISK` **真的走通全部闸门并选中了动作** | 验证日志 §7 第 1 条**未验证** |
| `outcome` | 触发后行为继续 / 停止两种走向 | T+10min 真的落 `outcomes` 行，且标签符合 `disengaged_ratio` / `continued_ratio` | §7 第 2 条**未验证** |
| `gates` | cooldown「差一分钟」vs「正好到点」；当天第 8 次 vs 第 9 次 | 边界值精确，不多不少 | 审查发现·闸门静默失效 |
| `degraded` | `data_status = unreachable` | 落 `skipped=1`，且不当成可信结论 | 审查发现·最严重之二 |
| `sleep_gap` | 制造 > 2×窗口的空档 | 跳过本轮评估 + `run_events` 落行 | 本版新增的健康信号（§7） |

**`degraded` 里 `NORMAL` 仍然会出现，这是设计而非缺陷。** `State` 是封闭枚举（§3），没有"无法判定"这个成员；引擎表达"无法判定"的方式是 `skipped=1` —— 它阻断全部干预路径，而 `state` 列留 `NORMAL` 占位。所以这条剧本该钉住的是**成对断言**：`skipped == 1` 且 `state == 'NORMAL'`，前者证明它没被当成可信结论，后者证明谁都不该把这个取值当结论读。原文写的"不判成 `NORMAL`"是在要求枚举装着它没有的 unknown，措辞已修订（2026-09-18）。

**`ladder` 的断言曾经比这一行弱。** 它只检查到 `PASSIVE_CONSUMPTION` —— 因为 `high_risk_minutes` 配成 65 而窗口只有 60，那一档永远不可达。**让断言迁就代码，等于把一个死状态合法化**；现在配置层拒绝那种组合，断言也恢复了（§15 风险 9）。

**`gates` 用 1 分钟步长，不是 5 分钟。** 5 分钟步长只能给出"间隔 25 被挡 / 30 通过"，边界到底压在哪一点上（`cooldown-1` 挡、`cooldown` 过）根本测不到 —— 而"边界值精确，不多不少"要的正是那个点。对应地，断言不再只是 `len(interventions) <= daily_cap`，而是**恰好等于** `daily_cap`，并且两侧都要看到：第 `cap` 次通过时的计数值、第 `cap+1` 次被挡时的计数值。只看被挡的那一侧，无法区分"上限生效"与"根本没跑到上限"。

**`ladder` 与 `outcome` 是其中最有价值的两个**（它们把 §1.1 的前两条从未验证变为已验证）。**`gates` 与 `degraded` 同样重要**：V0 的那两条最严重问题都是"154 个测试全绿之后才被发现"的 —— 它们不靠单元测试暴露，靠配置组合与真实数据暴露。回放器把它们变成回归用例，**让它们不可能再悄悄回来**。

### 6.5 `ActivitySource` 缝隙

`Scheduler.__init__` 目前写的是具体类 `reader: ActivityReader`，而 `Clock` 与 `Notifier` 都是 Protocol。新增 `activity/base.py` 的 `ActivitySource` Protocol（方法签名与 `ActivityReader.read` 一致），把"唯一可替换的数据源缝隙"在代码里立起来。

> **如实标注**：本仓库没有配置类型检查器（`pyproject.toml` 只有 `[tool.pytest.ini_options]`）。因此这个改动**不是为了静态检查通过**，纯粹是为了把缝隙写进代码、让回放器有据可依。收益真实但有限，不是架构升级。

### 6.6 能验证什么，不能验证什么

| | 项 |
|---|---|
| ✅ 能验**机制** | 三档阈值阶梯真的会触发；闸门组合真的按预期挡或放；T+10min 回执真的落 `outcomes`；跨天、跨 cooldown、`daily_cap` 边界；降级数据真的不误判 |
| ❌ 不能验**时机好不好** | 合成数据是人编的，不代表真实分布 |
| ❌ 不能验**分类清单准不准** | 同上 |
| ❌ 不能验**弹窗是否真的可见** | 需真实桌面环境，V0 已手工验证 |

**回放器把"需要等"变成"不需要等"，但不能把"需要真实使用"变成"不需要真实使用"。**

### 6.7 与 report 的配合

`--replay <剧本> --keep-db` 保留库到 `<store 所在目录>/replay/<剧本>/`，随后可用 `--report --db <该库>` 阅读它 —— 回放产出数据，report 消费数据，形成一条**不依赖真实时间**的完整验证回路。

**默认不保留**：写临时目录、跑完删除。理由与"绝不污染生产库"是同一条 ——
验证工具不该在磁盘上留下需要人记得清理的东西。保留是显式动作，所以给了 `--keep-db`。

**`ladder` 剧本的正午起点**：`START` 取**本机本地**正午（`datetime(...).astimezone()`），
不是写死一个 UTC 时刻。曾经写的是 `04:00 UTC` 并注释为"本地正午"，那只在 UTC+8 上成立；
换个时区整段剧本会滑进 `late_night`（本地 1:00–6:00）窗口，同一份剧本在两台机器上给出不同措辞。
取正午还有一层好处：整段剧本必然落在同一个本地日内，`daily_cap` 的跨天边界不会干扰断言。

## 7. 健康信号

### 7.1 为什么不需要心跳表

`ActivityReader.read()` 永不抛异常（§1.3）：采集侧的所有故障都会变成 `data_status` 的一个取值并**落行**。`evaluations.data_status` 已经是一份逐 tick 的完整断连日志。

因此 V0.5 不新增心跳表，只补齐 §1.3 表格里的 (a) 与 (c) 两种情况。

### 7.2 `run_events` 表

```sql
CREATE TABLE IF NOT EXISTS run_events (
  at     TEXT PRIMARY KEY,
  kind   TEXT NOT NULL,   -- 封闭枚举：'sleep_gap' | 'tick_error'
  detail TEXT NOT NULL    -- sleep_gap: 空档分钟数；tick_error: 异常类名 + 消息首行（截断至 200 字符）
);
```

只记录**异常**，不记录正常 tick —— 正常存活由 `evaluations.at` 派生。避免同一事实存两遍（与 V0 "`state_transitions` 由 `evaluations` 派生"同一原则）。

### 7.3 两处补丁

| 位置 | 现状 | 改为 |
|---|---|---|
| `scheduler.py:111` 休眠/唤醒提前 return | 静默跳过，不落行 | 一并写 `run_events(kind='sleep_gap', detail=空档分钟数)` |
| `run_forever` 的 `except Exception` | 只 `log.exception`，不落库 | 一并写 `run_events(kind='tick_error', detail=异常类名+消息首行)` |

### 7.4 三态判定

补完之后，"没有记录"这个现象**从二义变确定**：

| 看到什么 | 结论 |
|---|---|
| 有 `evaluations` 行 | 正常跑了 |
| 无行 + 有 `run_events` 行 | 有意跳过 / 出错（**可辨**） |
| 无行 + 无 `run_events` | **进程死了**（唯一解释） |

判定"此刻是否掉线"：`now - max(evaluations.at) > report.gap_threshold_minutes`。

**这一条一度只实现了一半。** 缺口列表（历史那半）做了，"此刻"那半没做 ——
于是 §10 里那句话（同一个键服务两个判定）只有一个判定是真的。现在
`report/queries.py::build_liveness` 实现它，`now` 由 `clock.now()` 显式传入
（保持纯函数，报告才可能在测试里固定到某一刻复现），输出里同时给出静默分钟数、
所用阈值，以及最后一条评估之后的 `run_events` —— 三样都给，读者才判断得出这个结论有多硬。

时钟回拨或库里出现未来行时 `silent` 为负，**一律不算掉线**：「未来有数据」不是「进程死了」。

### 7.5 两条硬约束

1. **`run_events` 绝不写进 `interventions`。** 否则运维告警会占用 `daily_cap` 配额、消耗 `cooldown`，并在 `outcomes` 里混进一堆不是干预的"干预效果"数据，使视图 4 的分层分析当场失效。
2. **健康告警绝不弹窗。** 告警的落点是 report 的视图（事后可判）。进程的自动恢复交给任务计划程序的"失败后重启"设置 —— 属部署配置，不是代码。

### 7.6 已知边界

若 `Store` 自身失效（磁盘满、库损坏），`run_events` 也写不进去，此时退化为"看起来像进程死了"。这是可接受的降级，但**必须写明** —— 否则将来会把一次磁盘故障误判成进程崩溃。

**第二处已知边界：`at` 是主键，同一秒内只能留一行。** 写入用的是 `INSERT OR REPLACE`，
同一时刻的第二条会**覆盖**第一条而不是并存。睡眠跳过与单轮异常不可能发生在同一秒
（前者当轮提前 `return`，不会走到异常路径），所以这是有意的取巧而非缺陷；
但它确实是一处边界：如果将来新增第三种事件类型，或常驻进程出现两个实例同时写，
先写的那条会静默消失。到那时应该给 `run_events` 换一个代理主键，而不是继续加事件类型。

### 7.7 常驻进程自身的日志

`run_events` 补上之后，「没有记录」只剩「进程死了」一个解释 —— 但**「进程死了」这件事
本身没有记录**。那两处补丁只覆盖 `run_tick_guarded` 抓到的异常，覆盖不了进程级退出。

实测踩到过：任务计划程序报 `LastTaskResult=0`（成功），而 `run_forever` 是死循环、
本不该返回；进程不见了，日志里一句话没有，`run_events` 也没有行。唯一线索是
一轮 tick 的间隔只有 2.8 分钟而不是 5.0。**这正是本版本要消灭的那类二义的另一个面。**

补法是给常驻进程自己的日志立三条规矩：

| 规矩 | 理由 |
|---|---|
| **启动时打一行**（pid / 分支 / schema / 库 / Screenpipe 地址 / 通道） | daemon 健康的一轮什么都不打印（记录落库，不重复存两遍），于是空日志既可能是「一切正常」也可能是「刚被重启过」。有启动行，重启历史才可读。分支必须在内 —— 曾经从错误的分支起过 daemon，它把 `user_version` 降级回 3 |
| **`run_forever` 结束时打一行**（`finally`，异常路径另记一行原因） | 三种结局因此可分：有「异常中止」= 抛出来的，原因就在同一行；只有「结束」= 循环自己走完了（那就是缺陷）；两句都没有 = 被外力杀掉 |
| **日志走 stdout、编码钉 UTF-8、不缓冲** | stdout 是给常驻模式的（其余模式的 stdout 要给 jq，所以它们的日志在 stderr）；不钉编码的话 Windows 会用当前 ANSI 代码页写出 GBK 字节，UTF-8 读就是乱码 |

**日志文件必须留档。** `Start-Process -RedirectStandardOutput` 是覆盖写：每次真正重启
都会把上一份截断成 0 字节 —— 于是「上一次为什么退出」的答案被下一次重启亲手删掉。
启动器因此改成先把旧日志改名留档（保留最近 5 份）。这条是部署约定，不是代码。

## 9. 数据模型变更（schema v3 → v6）

| 变更 | 内容 | 理由 |
|---|---|---|
| 新增表 | `run_events(at, kind, detail)` | §7.2 |
| 新增列 (v4) | `evaluations.entries_minutes REAL NOT NULL DEFAULT 0` | 区分"OTHER 类条目"与"明细缺失"，使视图 5 的锚点精确（§5.2） |
| 新增列 (v5) | `evaluations.fullscreen_state INTEGER`（**可空**） | 全屏信号（§4.5）。记原始值而非布尔，否则事后审不动准确率 |
| 新增列 (v6) | `interventions.channel TEXT`（**可空**） | 投递通道（§5.2 视图 3）。`--dry-run` 与真弹窗都记 `delivered`，不记通道就永远分不开排练与真事 |

迁移沿用 `_apply_incremental_migrations()` 的既有机制，`SCHEMA_VERSION` 递增到 6。

`fullscreen_state` 与 `channel` 都可空，语义相同：旧行留 `NULL` = 「当时没观测过」。
前者是"无法判定全屏状态"，后者是"通道未知" —— **都不伪造一个看起来正常的取值**。
这一点与 `entries_minutes` 的 `DEFAULT 0` 同样重要，理由相反：那里 0 是可疑信号，这里 NULL 才是诚实。

`channel` 的取值就是 `DeliveryResult.channel`（`foreground_popup` / `recording`）——
它本来就在对象上，只是过去没有被落库。这一列的代价是零：不需要新的采集、不需要新的字段。

`entries_minutes` 需在 `StateVerdict` 上新增同名字段（条目 `minutes` 之和），由 `engine` 计算 —— 与 `ent_minutes` / `gray_minutes` / `work_minutes` 同一处产出，保证口径一致。

**该 Python 字段刻意不给默认值。** `ent_minutes` / `gray_minutes` / `work_minutes` 三个同类字段都没有默认值；而 `0.0` 在这里恰好是"条目明细缺失"这个可疑信号本身 —— 给默认值等于让漏掉它的构造点静默产生假信号，使真正该被发现的漏判反而不触发锚点。全仓仅 7 处构造点（2 处在 `engine` 的共享 dict 内，5 处在测试 helper）。

> 与上表 SQL 列的 `DEFAULT 0` 不矛盾：那是给**旧行**读取用的兼容值（迁移层），这里说的是**新代码构造 `StateVerdict` 时**是否允许省略（契约层）。两件事。

**旧库兼容 —— 原表述有自相矛盾，已修订（2026-09-18）。** 原文说「对旧行，视图 5 的锚点判据**退化为使用 `total_active_minutes`**，并在输出中标注『该区间无 `entries_minutes` 记录』」。但同一节紧接着论证的正是：**用 `total_active_minutes` 当漏判判据会把「明细缺失」算成「漏判」，而这正是本版本存在的意义所在。** 两句话不能同时成立。

修订后的处理是：

- `DEFAULT 0` 使既有行可读，**但旧行不会因此变成漏判锚点** —— 两个差额都退化，它本来就不该产生锚点；
- 这些行的数量由 `VerdictBreakdown.entries_unknown` 数出来（`total_active_minutes > 0` 且 `entries_minutes <= 0`），并从视图 1 与视图 5 **两处**说出口；
- 说出口的内容就是它的真实状态：**"既不能算漏判，也不能算没漏判"**。不选一个方向硬凑一个结论。

**`gate_trace` 的序列化归宿在 `intervention/models.py`，这是有意决定（2026-09-18 记录）。** `dump_gate_trace` 与 `parse_gate_trace` 成对放在 `GateResult` 所在处，而不是下沉到 store、也不上收到 report：这个字符串的格式是 `GateResult` 这个数据结构的属性，读写成对同处才能防漂移 —— 改一半忘了另一半时，同一文件里的另一半立刻在测试里红。store 只存这列字符串，report 只是 `parse_gate_trace` 的消费者。

## 11. CLI 变更

```
statesense --check                          （V0）
statesense --once [--dry-run]               （V0）
statesense --daemon                         （V0）
statesense --report [--since 7d] [--format text|json]
                    [--views all|0,1,2,3,4,5] [--trace <ISO 时刻>] [--from-screenpipe]
statesense --replay <ladder|outcome|gates|degraded|sleep_gap|all> [--keep-db]
```

| 决策 | 理由 |
|---|---|
| `--report` / `--replay` 加入既有的互斥组 | 与 `--check` / `--once` / `--daemon` 同级，保持"一次只做一件事" |
| `--replay` 默认写临时库，跑完删除 | 绝不污染生产库，也不留垃圾 |
| `--replay --keep-db` | 显式要求保留时才写到 `<store 所在目录>/replay/<剧本>/`，可用 `--report --db <那里的库>` 继续读 |
| `--replay all` | 直接服务 §2 判据 1 |
| `--report` 默认不带 `--from-screenpipe` | 离线可读；回查 Screenpipe 是显式动作 |

**`--views` 的取值是封闭集合 `0,1,2,3,4,5`，未知编号必须报错退出 2。**
曾经实现里只认 1–4 且静默忽略其余值，于是规格与 `config.example.toml` 都在教用户敲
`--views 5`，敲下去却得到一片空白 —— 看起来像"这个视图没有数据"，而不是"这个编号不存在"。
排查方向从一开始就是歪的。**一个被忽略的参数比一个报错的参数危险得多。**

`--format json` 输出全部视图字段，因此 `--views` 对它无效 —— 这一点会向 stderr 说明，
而不是静默忽略。

**只有 `--report` 认的参数在 `--help` 里标注了「仅 --report 有效」**（`--since` / `--format` /
`--views` / `--trace` / `--from-screenpipe`），`--dry-run` 标注「仅 --once / --daemon 有效；
--replay 恒为不弹窗」。这些参数与模式共用一个解析器，无法在语法层互斥；
把这些话写进帮助文本，是让「我传了它却没生效」这件事在敲命令时就能被看见。

`--keep-db` 是唯一一个只服务 `--replay` 的参数，它不属于互斥组。

**`--check` 额外打印一次全屏信号**（原始取值 + 人话解释）。§4.5 那条自动推断是全仓唯一
一处"自己看环境"的逻辑，自检时必须能看见"这台机器上它现在读到什么"——
否则信号整条静默失效、而配置看起来完全正确，正是这一类缺陷最典型的形态。

**`--report` 遇到 schema 低于当前版本的库直接拒绝（退出码 2），不做迁移。**
它是只读命令，"顺手迁移"就是写库。提示用户先跑一次 `--once`。这是比 §12 原文
更强的立场：宁可拒绝，也不在一个号称只读的路径上动数据。

**`--report` 是只读命令**：不构造任何写入语句。`Store` 新增的方法一律以 `fetch_` / `list_` / `count_` 开头，便于评审时一眼确认。

## 12. 错误与边界

| 情形 | 行为 |
|---|---|
| `--report` 时库不存在 | 明确报错并提示先跑 `--once` 或 `--daemon`，退出码 2 |
| `--report` 时库为空（零行） | 正常输出"区间内无任何评估记录"，**不是错误**（这正是"进程从未跑起来"的观测结果） |
| `--report` 时库 schema 低于当前版本 | 拒绝并提示先跑一次 `--once`，退出码 2，**绝不顺手迁移** |
| `--from-screenpipe` 但 API key 缺失 | 仅二级视图跳过并提示，一级视图照常输出；退出码 0 |
| `--from-screenpipe` 但没有锚点 | 明确打印"本次区间内没有锚点，无需回查"，退出码 0 —— 沉默会被读成"参数没生效" |
| `--from-screenpipe` 但 Screenpipe 不可达 | 同上，并在输出中标注"明细不可用" |
| `gate_trace` 解析失败 | 该行计入"闸门数据损坏"计数并跳过，不中断整份报告 |
| `--views` 含未知编号 | 报出可用编号，退出码 2 —— **不静默忽略** |
| 配置文件某节含未知键（拼错的名字） | 包成 `ConfigError`，退出码 2 —— 否则 dataclass 构造抛的 `TypeError` 会变成 traceback + 1 |
| `thresholds.high_risk_minutes` 大于 `schedule.window_minutes` | 启动即拒绝：该状态永远不可达，它专属的动作是死代码。提示两条修法（降阈值或加长窗口） |
| `--replay` 指定未知剧本名 | 列出可用剧本，退出码 2 |
| `--replay` 剧本断言失败 | 打印期望 vs 实际，退出码 1 |
| 旧库缺 `entries_minutes` 列 | 迁移自动补列；历史行按 §9 的降级方式处理（计数并说明，**不**当作漏判锚点） |

| 对象 | 方式 |
|---|---|
| `report/` 聚合函数 | 单元测试，喂合成 row 序列 —— 纯函数，不需要数据库 |
| `report/` 渲染 | 单元测试，断言关键字段出现在输出中 |

| schema v6 迁移 | 单元测试：从 v1/v3 库升级，断言新表新列（`entries_minutes` / `fullscreen_state` / `channel`）存在且旧行可读 |
| 五个剧本 | pytest 用例，各自断言期望结果（这是 `replay/` 的第一等消费者） |
| 回归 | 现有 154 个不得退化（2026-09-18：**343 passed**） |

**回放的密闭性另有一组针对性测试。** 机制层面：把 `Scheduler` 的兜底探针
（`statesense.scheduler.default_probe`）换成"永远说正在全屏游戏"，剧本结论必须一字不变；
对照组则让剧本自己声明 `fullscreen_state=2`，此时未命中规则的条目必须被提权。
两条合起来才证明"信号确实穿过了 Scheduler → store → 落行整条链路，且没有偷读真实环境"。

**`check_scenario` 的默认落点也有一条测试**：跑完之后配置目录下不该出现 `replay/`
（默认走临时目录并删除），而 `keep_db=True` 时必须出现在文档写明的位置。

**全屏信号（§4.5）另有一组针对性测试**：`is_gaming` 的取值边界、探针在非 Windows/调用失败/枚举外取值时返回 `None`、`classify` 只提权 `OTHER` 而不动 `WORK`/`GRAY`、数据不可信时不提权，以及一条**带对照组的端到端测试**（同一个未命名游戏，开信号触发、关信号漏掉）。另有一条在 Windows 上真实调用 API 的测试，锁定"这台机器上它确实可用"—— 若哪天开始失败，说明整条信号的前提没了。

**测试样本沿用 V0 的决定**：以模块内联 dict 形式写在受访测试里，不另建 `tests/fixtures/*.json`（V0 验证日志 §9.3 已记录该决定）。回放剧本是**场景**而非样本，因此放在 `replay/` 而非 `tests/`：它同时被人和测试消费。

> 补一句防误读（2026-09-18）："不另建"管的是**数据样本**。`tests/conftest.py` 里的配置 fixture（以 `config.example.toml` 为底、只把 store 路径换成临时目录）是**配置脚手架**，不是样本 —— 没有它，每个测试都要复刻一遍"哪些键必须存在才能 load 成功"，那才是真正的漂移源。它不在本决定的豁免范围内，也不该被搬走。

| 14 | ~~**`--dry-run` 的排练与真实干预在库里无法区分**~~ | 两者都走 `delivered` 分支，`interventions` 表里长得完全一样。于是"今晚到底有没有真的弹过窗"这个最基本的问题答不上来，而视图 3 / 视图 4 的结论会同时被两种数据污染 | **已解决（2026-09-18）。** schema v6 新增 `interventions.channel`，值取 `DeliveryResult.channel`（`foreground_popup` / `recording`）—— 它本来就在对象上，只是没被落库。视图 3 增加"投递通道"一行。旧行留 `NULL` = 通道未知 |

| 16 | **5 天窗口内真实触发次数可能极少** | 实测（2026-09-17）：一整晚重度使用只产生 **1 次**真实干预 —— 因为 `ratio_min=0.75` 挡掉了 133/140 轮 | 这正是判据 4 要回答的问题，**不是缺陷**。但它意味着"视图 4 的分层分析"在短期内样本量必然不足，不得据此下"什么干预有效"的结论（与风险 2、5 同一条纪律） |
